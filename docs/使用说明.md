# C 源码学习设计文档 Skill

这个技能让工作 AI 围绕你指定的 C 文件阅读源码，生成一份中文 Markdown 学习设计文档，包含文件级模块边界、接口契约、模块交互、4+1 视图和可渲染的 PlantUML 图代码。

它面向你使用的 GLM 5.2 + 改造版 OpenCode，采用通用 `SKILL.md` 格式，不依赖模型专属 API。实际加载行为仍取决于你的 OpenCode 改造方式；未在你的环境中实测。

## 安装

解压 `c-code-design-doc.zip`，将其中的整个 `c-code-design-doc` 文件夹复制到代码库的 `.opencode/skills/` 目录，得到：

```text
你的代码库/
└── .opencode/
    └── skills/
        └── c-code-design-doc/
            ├── SKILL.md
            ├── assets/
            │   └── design-doc-template.md
            └── references/
                ├── diagram-guide.md
                └── visual-style.md
```

`SKILL.md` 是执行指令；`assets/` 提供文档模板；`references/` 提供绘图语义、规范和七类语法示例。请整体复制，保留文件名及目录结构。

这是 OpenCode 官方支持的项目级技能位置。也支持全局路径 `~/.config/opencode/skills/`；改造版若变更了发现路径，使用你们的实际配置。[OpenCode 官方技能文档](https://opencode.ai/docs/skills/)

## 使用

在代码库的工作会话中，替换下面的目标文件名后发送：

```text
请加载并执行 c-code-design-doc 技能。
分析 src/net/session.c 和 include/net/session.h，
重点解释初始化、一次请求处理、回调、错误传播和资源释放。
必要时追踪直接调用方与依赖。
构建配置使用仓库当前可确认的配置；无法确认的条件分支分别说明。
输出到 docs/learning/session-design.md。
```

如果你只想理解一条链，也可以这样说：

```text
使用 c-code-design-doc 技能，从 src/protocol/frame.c 的 frame_receive()
出发，解释一帧数据如何经过解析、分发和响应。
文档保留相关文件的接口契约、4+1 视角和关键 UML 图，
重点分析这条链，遇到无法解析的回调明确标注。
```

以上文件和符号只是调用示例，不是你仓库的真实路径。

如果改造版没有发现技能，直接让 AI 读取文件：

```text
请读取 .opencode/skills/c-code-design-doc/SKILL.md 并按它执行本次任务。
附件路径相对这个 SKILL.md 所在目录。
写作前读取 assets/design-doc-template.md，
绘图前读取 references/diagram-guide.md 和 references/visual-style.md。
然后分析我指定的 C 文件并生成学习设计文档。
```

这种回退方式需要 agent 有读取源码、搜索和写入 Markdown 的能力。没有假定某个 `/命令` 或特定 `skill()` 参数适用于你们的改造版。

## 文档的内容约束

- **文件级模块**：使用仓库相对路径识别模块；同名文件不混淆；不按名称猜测 `.c` 与 `.h` 的对应关系。
- **有证据的结论**：关键行为附源码路径、符号和定位；区分确认事实、推断与未知。
- **完整的 4+1 关注点**：逻辑、开发、进程、物理、场景；视图没有充分依据时说明缺口，不编造拓扑。
- **准确的接口与交互**：区分包含、调用、回调绑定、消息传递、构建依赖；说明所有权、有效期、错误传播及执行约束。
- **清楚的图**：每张图围绕一个问题，统一文件与符号命名，箭头具有明确语义；代码块可以独立渲染。
- **便于学习**：先概览，再看边界与场景，最后给出按文件和函数组织的阅读路线。

4+1 是五种观察角度，图数按实际信息决定。对于普通 C 库，进程和物理视图可能只需解释宿主边界及未知项；不能把一个文件画成独立进程。

## 图的专业内容与视觉风格

`references/visual-style.md` 将建模与外观分开验收。逻辑图中的接口以操作契约命名，头文件作为声明来源；时序图使用运行时角色并附实现文件；消息流与函数调用分别表达。构建输入和队列数据流使用明确的自定义图例。

默认采用白底、深蓝灰文字和线条、浅蓝目标节点、中性灰依赖，统一图题、字号层级和留白。没有渐变、阴影、手绘装饰或彩虹配色；目标角色同时用文字标识。

每个图块包含独立的样式设置。验收要求包括：文字无乱码和遮挡，线不穿过无关节点，端点清楚，正常尺寸可读，同一文档样式一致。过密图应拆分，不用微小字体掩盖拥挤。两张完整示例代码见压缩包中的 `专业图示样例.md`。

Chrome 扩展可能忽略部分样式设置或重新布局；下述本地原版 PlantUML 预览不能代替目标扩展实测。需要严格统一外观时，应选用支持对应 skinparam 的渲染器。

## 在 Chrome 中渲染

默认图语言是 **PlantUML**，用于组件、接口、时序、部署、状态及必要的数据结构图。生成的设计文档保留图代码，不依赖预先生成的图片。

可先使用免费的 [docu.md Markdown Viewer（Chrome 商店）](https://chromewebstore.google.com/detail/documd-markdown-viewer/jekhhoflgcfoikceikgeenibinpojaoi)。作者官网说明没有付费层；作者文档支持 Markdown 中的 `plantuml` 围栏。[免费说明](https://docu.md/)、[PlantUML 支持说明](https://docu.md/features/diagrams/plantuml.html)

操作步骤：

1. 在 Chrome 安装扩展。
2. 打开 `chrome://extensions/`，进入该扩展的详情。
3. 开启“允许访问文件网址 / Allow access to file URLs”。
4. 将生成的 `.md` 文件拖入 Chrome，检查正文和图。

以上本地文件访问步骤来自 [作者 Chrome 使用说明](https://github.com/markdown-viewer/docs/blob/main/platforms/chrome.md)。

按作者说明，常规预览在本地处理。该扩展通过转换器处理 PlantUML，并非原版 Java PlantUML 引擎，因此不能保证全部语法与布局完全相同。技能已使用基础语法并避开远程宏库；如果某张图不显示，先核对语法，再用原版 PlantUML 对照检查，保留原始 Markdown 图代码。[扩展渲染器源码](https://github.com/markdown-viewer/markdown-viewer-extension/blob/main/src/renderers/plantuml-renderer.ts)

扩展文档列出了时序、组件、状态等图；部署图由其底层转换库列为支持类型，最终仍需在你安装的版本中确认显示效果。[底层转换库](https://www.npmjs.com/package/@markdown-viewer/draw-uml)

这里核查了官方页面与作者资料，没有替你安装扩展，也没有实测扩展界面。资料核查日期：2026-10-20。
