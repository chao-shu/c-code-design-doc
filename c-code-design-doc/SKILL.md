# C 源码学习设计文档

将实际读到的 C 源码整理为准确、干练、易懂、专业的学习设计文档。文档描述当前实现；设计意图只有在证据支持时才能作为事实。默认中文，保留代码中的路径、符号、宏和错误码原名。

适配具有文件读取、搜索和写入能力的 agent；不依赖特定模型、子代理、专有工具或联网服务。使用当前环境已有工具，搜索优先使用 `rg`，没有时使用等效工具。

本技能目录中的资源路径均相对本 `SKILL.md`，不是相对代码库根目录。先确认技能的实际目录再读取资源。

## 交付约定

- 默认交付一份 UTF-8 Markdown 文档，图直接使用独立的 `plantuml` 围栏代码块；每块包含完整的 `@startuml` / `@enduml`。不以图片、外部图链接或多个 `.puml` 文件代替正文图代码。
- 用户指定的文件是分析中心。模块标识使用仓库相对文件路径，例如 `src/net/session.c`；无歧义时图中可缩写为 `session.c`。同名文件必须保留足以区分的路径。
- `.c` 是实现文件，`.h` 是接口、类型或内联实现的来源。只有检查声明、定义和包含关系后，才可把它们组合描述；不能因为同名就假定一一对应。
- 输出优先采用用户指定路径，其次采用仓库已有文档目录；没有约定时使用 `docs/learning/<主题>-design.md`。主题由目标文件或用户场景命名。未获代码改动任务时，只写本次文档和必要的临时分析文件。
- 产出内容按 [文档模板](assets/design-doc-template.md) 组织；绘图前读取 [绘图规范](references/diagram-guide.md) 与 [视觉规范](references/visual-style.md)。默认采用白底、深色文字、蓝灰配色的工程文档风格，统一图题、字号、节点角色与线条；每图内嵌独立样式。模板提供结构，所有提示和示例都要替换或删除。

## 1. 确认分析边界

确定代码库位置、目标文件/入口、用户关心的行为、构建配置及输出位置。已有上下文能确定的直接执行。

用户只给模块名时，搜索匹配文件，结合调用方和目录判定。若存在多个无法判定的同名目标，先列出候选并询问；没有代码或无法访问目标时，说明缺少什么，不生成看似完整的源码设计文档。

记录当前提交标识（可取得时）、相关未提交改动、目标平台与关键宏。不运行构建脚本来猜测配置；先读已有构建描述、配置头和编译数据库。配置不能确认时，注明“构建配置未确认”，分别解释相关条件分支，不能把互斥实现拼成一条运行路径。

扩展阅读范围到解释目标所必需的：

1. 声明、类型、常量、条件编译和实际实现。
2. 主要直接调用方、直接依赖及关键回调的注册/绑定位置。
3. 与主场景有关的初始化、正常处理、错误回退和释放路径。
4. 能证明构建、执行上下文或部署关系的少量配置与启动代码。

当关键接口、主场景、生命周期和依赖边界已经能解释，或剩余关系确实不可解析时停止扩展；未知项进入文档。不能因依赖很多而默认扫描整个仓库。大范围任务按场景分批记录证据，再统一写一份文档。

## 2. 建立事实与证据

先读实现，再做摘要和图。搜索结果、函数名、注释和旧文档只能作为线索；必须查看关键定义、调用点及必要上下文。类型声明反映契约，实现反映行为；发生冲突时写明两者，不替实现补上不存在的检查。

使用简短的工作记录保存“结论 → 路径 + 符号 + 行区间 → 条件/限制”。工作记录不需要作为思考过程交付。

正文区分三类信息：

- **已确认**：可直接定位到源码、构建文件、配置或实际观察。正常事实不必逐句贴标签，但关键结论应附证据编号。
- **推断**：列出依据与推断范围，例如“推断调用期间需由调用方保持缓冲区有效”，不能写成已经声明的 API 保证。
- **未知**：明确缺少的绑定、调用方、配置或运行记录，以及最有用的下一处检查位置。“没找到”必须说明搜索范围。

证据使用 `[E01]` 等稳定编号，文末列出仓库相对路径、准确符号、实际读取的行区间及支持的结论。正文表格、图后说明共用编号。行号不可靠时用路径 + 符号 + 定位说明，禁止估造行号或执行结果。非 Git 仓库注明版本标识不可得。

### C 项目必须正确区分的关系

| 关系 | 应核实的事实 | 不能据此推出 |
|---|---|---|
| `#include` | 当前分支中的文本包含、类型或声明依赖 | 模块运行时一定调用被包含模块 |
| 函数调用 | 调用点、可见声明、定义/链接选择 | 名称相同的函数就是同一实现 |
| 函数指针/回调 | typedef、赋值/注册、调用点、可选目标、执行上下文 | 回调天然异步；接口声明能证明具体绑定 |
| 构建与链接 | 源文件清单、目标、平台选择、链接脚本/选项 | 仓库里的所有 `.c` 都进入当前产物 |
| 数据访问 | 谁读写、谁分配/释放、状态何时改变 | 指针成员代表所有权；`volatile` 代表线程安全 |

额外检查影响目标行为的 C 细节：

- `static` 函数/对象的文件作用域；`extern` 声明和真实定义；头文件中的宏和 `static inline` 实现。
- 宏展开中的隐藏调用和副作用；`#if`、弱符号、链接替换、平台实现、生成代码以及测试替身。不能仅凭文本搜索认定当前有效实现。
- 结构体与不透明句柄的有效期、借用/复制/转移、缓冲区长度和单位、空指针前提、返回值及错误码传播。有回调时分别跟踪函数返回码与回调结果，不能把“提交被接受”直接解释为“操作已成功完成”。
- 初始化与销毁的配对、失败后的部分初始化清理、重入、共享全局状态、锁/原子/中断临界区及阻塞位置。

只展开与用户目标相关的细节。没有锁不能证明无并发；找到锁也不能直接宣布线程安全。不得将静态阅读结果写成运行测试结论。

## 3. 建立 4+1 视图

4+1 是五种观察角度，不是固定五张图。每个视图都要有简短结论和证据状态；不同视图允许引用同一张图，但必须解释该视图的关注点。上下文图是额外的阅读入口，不替代任何视图。

| 视图 | 要回答的问题 | C 项目的表达与合适图型 |
|---|---|---|
| 逻辑视图 | 提供什么职责、操作和数据抽象？ | 以文件标识组件，用接口和必要的 `struct` 关系表达职责分工；逻辑分组注明对应文件 |
| 开发视图 | 代码如何组织、包含、编译和链接？ | 文件/包/制品依赖图；区分 `.c`、`.h`、库和构建目标 |
| 进程视图 | 操作在哪个进程、线程、任务、事件循环或 ISR 中执行？如何协作？ | 执行上下文关系图或带上下文说明的时序图；区分同步调用、消息、队列、锁和回调 |
| 物理视图 | 软件制品运行在哪些节点/设备/执行环境，边界如何通信？ | UML 部署图；只画配置或代码能支持的节点及部署关系 |
| 场景视图（+1） | 一次具体使用如何穿过上述结构？ | 代表性的正常路径，以及有证据的关键失败/边界路径；以 UML 时序图为主 |

进程视图不等于函数流程图，物理视图不等于目录树，开发视图不等于运行调用图。不要用 C4 的四种层级替代 4+1。

对于纯库、局部文件或未提供系统上下文的情况，明确“宿主执行上下文未确认”“物理部署未确认”，写出已经确认的接口边界即可。经证据确认是单线程/单节点时可以简化表达。不能为了每个视图都有图而虚构线程、服务器、数据库、硬件或网络。

以一个主要场景贯穿各视图：接口表里的函数、逻辑图中的文件、开发图中的产物和部署图中的制品应能相互对应。对暂时无法对应的项标明缺口。

## 4. 编写学习设计文档

按“先整体、再边界、再交互、再细节”的顺序写：

- 开头用一小段说明模块解决什么问题、接收什么输入、输出/副作用是什么，以及读者最应记住的协作关系。
- 模块表记录文件、职责、关键公开接口和主要依赖；内部函数只选架构关键点。
- 接口契约写前置条件、参数及单位、所有权/有效期、返回/错误、状态副作用及执行限制。宽表可以按接口拆成短条目；未经声明或证明的保证标为未知/推断。
- 主场景解释触发条件、真实函数链、状态/数据变化和结果；失败场景写触发分支、返回传播、资源清理和可见状态。没有失败处理就如实说明。
- 只有存在真实状态集合和迁移时才画状态图；存在关键 C 数据关系时才用带 `<<struct>>` 等标注的类图。不要把每个 C 文件伪装成有成员方法的面向对象类。
- 用证据解释“为何这样设计”；若只是自己的理解，标为设计解读。需要建议时单独标成建议，不混入现有实现。
- 结尾给出可执行的阅读路线：先读哪个文件的哪个符号、理解什么、随后追到哪里。疑点只保留影响理解的项目，并给下一步验证入口。

语气采用技术设计说明：短段落、明确主语、具体动词。术语首次出现给简短解释。表格用于对比，代码片段只保留解释关键机制所必需的部分。

删除泛化赞美、重复总结、逐行翻译源码、与目标无关的知识讲义，以及没有来源的性能、可靠性、复杂度和“设计模式”判断。不用固定字数或图数填充内容。

## 5. 核对与交付

写完后回到源码抽查核心结论和全部图中的关键关系，并检查：

1. 目标范围、提交/工作区状态和配置是否准确；互斥分支是否分开。
2. 文件、符号、接口与图是否一致；图中的每条关键边是否有实际证据或显式未知标注。
3. 回调绑定、同步/异步、执行上下文、错误路径、内存所有权是否被正确表达；调用图是否混入纯包含关系。
4. 五种视角是否均有解释；证据不足的视图是否如实保留缺口。
5. 所有图块是否完整、别名唯一、参与者显式声明、条件/循环/分支闭合；UML 接口契约与头文件制品是否分清。
6. 视觉是否按规范验收：文字无乱码/裁切/遮挡、连线不穿过无关元素、端点与标签清楚、正常尺寸可读、全篇样式一致。颜色只作强调，不能代替关系语义。
7. 是否已删除模板提示、演示名称、空章节和重复内容；文档是否真正写入目标文件。

如果环境已有可用的本地 PlantUML，提取图代码到临时目录做语法检查，并在具备预览能力时逐图检查内容、布局和中文显示；报告实际完成的检查。若没有渲染器，做静态核对并明确“未进行渲染验证”，仍交付可读文档。不要因缺少渲染器自动安装软件或向公网发送项目图代码。

最终回复只需说明文档位置、覆盖的文件/场景、重要未知项以及图的验证状态。没有写文件能力时，交付完整 Markdown 内容并明确尚未保存。
